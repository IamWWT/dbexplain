性能飞跃

01Schema 采集：从 N+1 到批量查询

这是本次发布最硬核的优化。在 v0.1.6 及之前，dbexplain 对 PostgreSQL 和 MySQL 做 Schema 采集时，采用 N+1 查询模式：每个表单独查询 columns + indexes + foreign keys。100 个表 = 400-600 次数据库往返。

v0.1.7 将其重构为 per-schema 批量查询：在 tables 循环之前，一次性查出整个 schema 的所有 columns/indexes/FK，Go 侧用 map 按表名分组。100 个表从 400-600 次往返降至 ~7 次。

场景优化前优化后提升
PG 100 表采集 ~300 次查询 ~3 次 100×
MySQL 100 表采集 ~500 次查询 ~5 次 100×
MySQL 100 表 + op_stats ~600 次查询 ~6 次 100×
原理很简单：数据库的瓶颈不是单条 SQL 的执行速度，而是网络往返次数（RTT）。将 300 条独立查询合并为 3 条批量查询，网络开销从 300 RTT 降为 3 RTT。
information_schema.COLUMNS WHERE TABLE_SCHEMA=? ORDER BY TABLE_NAME, ORDINAL_POSITION — 一次查出全部表的全部列。

02两个新 Flag：按需跳过，不采集多余数据

很多场景下，你只需要表结构，不需要样本数据或性能指标。v0.1.7 新增了两个全局 flag：

🔇
--no-sample
跳过 SELECT * ... LIMIT 1 样本行采集。纯结构分析场景 CPU 时间减半，100 表省 100 次查询。
⏭️
--skip-opstats
跳过 MySQL performance_schema op stats 采集。100 表省 100 次查询。MySQL 独有。
# 只采集结构，不要样本数据，不要性能统计
dbexplain -dsn 'mysql://user:pass@host:3306/mydb?label=test' \
  --no-sample --skip-opstats --human

03CSV/Excel 流式读取：大文件不再撑爆内存

此前，SELECT * FROM file LIMIT 10 会把整个文件读入内存后才截断前 10 行。200MB 的 CSV = 必须占用 200MB 内存。

v0.1.7 改为流式读取：

1
CSV：使用 csvReader.Read() 逐行读取，读到 limit 行即停。内存占用 O(limit) 而非 O(N)。
2
XLSX：使用 excelize.Rows 迭代器替代 GetRows()，逐行 yield，不加载整个工作表。
注意：流式读取仅在 SELECT * LIMIT N 快速路径中生效。涉及 WHERE/GROUP BY/JOIN/聚合 的查询仍需要全量数据，走原有路径。

04inferRefs 加索引：1000 表从千万级降到万级

外键推断函数 inferRefs() 此前用 O(N²) 全表扫描匹配列名。1000 个表、平均每表 20 列 = 2000 万次比较。

v0.1.7 增加了 map[name][]tableEntry 倒排索引：

// 优化前：遍历全部表匹配列名
for _, tgt := range tables {  // O(N) per column
    ...
}

// 优化后：map lookup O(1)
nameIndex := map[string][]tableEntry{}
for _, e := range tables {
    nameIndex[strings.ToLower(e.table.Name)] = append(nameIndex[...], e)
}

// 内层循环
for _, tgt := range nameIndex[stemLC] { ... }  // O(1)

效果：1000 表的场景从 ~2000 万次比较降至 ~2 万次，千倍级提升。

Agent 体验

05Prometheus 行输出：LLM 终于能看懂指标了

这是 v0.1.7 对 AI Agent 最重要的体验改进。此前，dbexplain 采集 Prometheus 只输出表名和列结构（_labels 表有 label_name、_metrics 表有 metric_name/type/help/unit）。LLM Agent 只知道「有哪些 metric」，不知道「这些 metric 长什么样」。

v0.1.7 在 JSON 输出中增加了 rows 字段：

// 以前：只有表结构
{
  "name": "_labels",
  "columns": [{ "name": "label_name", "type": "text" }]
}

// 现在：表结构 + 样本数据行
{
  "name": "_labels",
  "columns": [...],
  "rows": [
    { "label_name": "instance" },
    { "label_name": "job" },
    { "label_name": "__name__" },
    ...  // ~206 条 label 名
  ]
}
为什么这很重要？ VeinMap 等 LLM Agent 做 NL→PromQL 语义匹配时，需要知道具体的 label 名和 metric 元数据。以前只能看到「有 206 个 label」，现在可以直接消费这 206 条样本数据做精确匹配。这是 Agent 智能问数的 P0 阻塞解除。

06dbexplain check：一键验证全链路连通性

新增的 check 子命令可以一次性验证所有 DSN 的语法正确性和数据库连通性：

# 自动加载 .env.dbexplain，检查全部 DSN
dbexplain check

# 只检查特定 label 的 DSN
dbexplain check --label my-prom

# 输出示例：
No. EnvKey Label              Kind       Host:Port             Syntax  Connect
── ────── ─────────────────── ────────── ──────────────────── ─────── ───────────────
1   DB1   my-mysql            mysql      192.168.1.100:3306   ✅ OK   ✅ OK 42ms
2   DB2   my-prom             prometheus 192.168.0.127:9090   ✅ OK   ✅ OK 156ms

支持 --dsn、--config、--timeout、--label 参数，密码自动脱敏，退出码反映失败项。从 v0.1.8 起已彻底移除 --env 参数，始终自动加载配置文件。

安全加固

07CTE 写操作拦截 & DSN 密码兼容

CTE 写检测加固

v0.1.7 修复了一个 sqlguard 只读校验绕过漏洞：WITH x AS (SELECT 1) INSERT INTO y VALUES (1) 可以绕过之前的检测。三层加固：

1
WITH 检测提前到 AST 解析之前，不再依赖 AST
2
containsCTEWrite() 增加主查询体写动词检查
3
修复 Go 经典陷阱：break 在 switch+for 嵌套中只跳出 switch 的语义问题（改用 labeled break）

DSN 密码中的 # 字符

Go 的 url.Parse 会将密码中的 #（如 redis://:pwd#123@host）解释为 URL fragment，导致解析失败。新增 escapeUserinfoHash() 预处理，自动转义 userinfo 段内的 # 为 %23。

关于 CPU 使用率：此前用户反馈 dbexplain 进程 CPU 使用率高，主要在 collect 操作中。经分析发现，主要瓶颈不是本地 CPU 计算，而是数据库 IO — N+1 查询模式下大量的网络往返等待。v0.1.7 的批量查询优化将 400-600 次往返降至 ~7 次，IO 等待时间大幅缩减，CPU 使用率自然下降。

接下来的方向：持续优化大 Schema 场景的性能，完善 Prometheus DSL 的 SQL 兼容性，以及更多企业级功能。
